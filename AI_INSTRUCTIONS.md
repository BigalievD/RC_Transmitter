# RC Transmitter — AI Instructions

Обновлено: 2026-11-23. Этот документ задаёт общие правила для всех чатов и AI-агентов, работающих над проектом.

## 1. Источники истины
1. Актуальный код и конфигурация — репозиторий `BigalievD/RC_Transmitter`, ветка `main`.
2. Задачи и их статусы — GitHub Issues. Главная организационная задача: RC-001 (#2).
3. Договорённости из предыдущих чатов — исторический контекст, а не доказательство присутствия кода в `main`.
4. Не объявлять сборку, тесты на устройстве или реализацию завершёнными без подтверждения.
5. Перед изменениями читать актуальные затрагиваемые файлы и сверять с историей решений.

## 2. Техническая база
- Целевая платформа: ESP32-P4; Arduino + PlatformIO.
- Интерфейс: LVGL 9.5, EEZ Studio.
- Ориентир по поведению передатчика: FrSky ETHOS 26.2.0; совпадение подтверждать отдельными тестами.
- Аппаратная конфигурация по истории разработки: четыре ADS1115, два MCP23017, 14 конфигурируемых переключателей. Проверять соответствие текущей ревизии платы.
- Архитектурные модули: InputManager, Mixer, Source, Switch, Trim, VarProcessor, SystemEvent, SD и UI. Реальное расположение и интерфейсы сверять с репозиторием.

## 3. Правила разработки
- Не редактировать автоматически сгенерированные EEZ Studio файлы вручную; менять исходный UI-проект и регенерировать код в согласованном процессе.
- Source и Active Conditions — разные сущности; не смешивать их обработку.
- Сохранять совместимость модели и её сериализации; изменение формата требует отдельного согласования.
- Изменять минимально необходимое количество файлов; выдавать только изменённые файлы.
- Сначала формулировать план и критерии проверки, затем реализовывать и тестировать.
- Не расширять лимиты 64 микса и 16 Actions до финального этапа без отдельного решения.
- Все новые статические переменные объявлять до первого использования.
- Однострочное действие в условии оформлять компактно: `if (condition) action();`. Для нескольких действий использовать фигурные скобки.
- Сигнатуры функций и объявления параметров размещать на одной строке, насколько это допускает читаемость.
- Не вносить несогласованные изменения в логику Flight Modes, Fade, Active Conditions и Mixer при работе над другой подсистемой.

## 4. Известное состояние (исторический срез, НЕ аудит текущего main)
- Free Mix и Aileron Mix: сообщалось о реализации; другие типы миксов не подтверждены.
- Flight Modes, Active Conditions, Fade In/Out, быстрое переключение FM1→FM2→FM1 и сохранение после перезапуска: функционально проверены по сообщению пользователя от 2026-11-10.
- Mix Engine: известны изменения для Weight ±500%, графика Mixes ±500% и runtime-ограничения ±200%; проверить реализацию в текущей ветке.
- Trim Behaviour: Off/Easy/Independent per FM и Custom (Unplugged, Normal, Equal Default, Offset + Default), до 20 строк Behaviour; статус НЕ завершён: в Trims → Behaviour → Active Condition отсутствует пункт Flight mode (замечание 2026-11-17).
- Для ряда патчей не подтверждены полная PlatformIO-сборка и испытания на ESP32-P4.
- Ранее принято решение использовать Half range из `objects.obj221`; резервное создание в runtime не восстанавливать без обсуждения.
- Клавиатуру Trims разрабатывать на последнем этапе соответствующей подсистемы.

## 5. Процесс задач
Каждая задача должна содержать: ID, цель, текущее поведение, ожидаемое поведение, затронутые файлы, зависимости, критерии приёмки, результаты тестов.
Статусы: Planned → In Progress → Review/Testing → Done; Blocked — для препятствий. Не считать закрытый Issue доказательством аппаратной проверки.
После изменения фиксировать: что изменено, что проверено, что НЕ проверено, оставшиеся риски и следующий шаг.

## 6. Правила для отдельных чатов
- В начале работы читать этот документ и релевантные GitHub Issues/файлы.
- Не полагаться на память других чатов как на актуальный код.
- Не объявлять гипотезы фактами; отмечать неподтверждённое.
- Не менять другие подсистемы без явной необходимости и согласования.
- При завершении передавать краткую сводку: Issue, файлы, решения, проверки, ограничения, дальнейшие действия.
- Секреты, токены и пароли не сохранять в репозитории или публичной документации.
